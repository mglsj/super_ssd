## Python basics (Q1–Q8)

### Q1. The abstract machine

What is the primary advantage of programming in Python's "Abstract Machine" compared to the "Exact Machine"?

- A) It allows direct control over hardware registers and memory addresses
- B) It enables programmers to think at a higher level of abstraction while the interpreter handles low-level details
- C) It provides faster execution speed for mathematical computations
- D) It requires less memory usage for the same programs

**Answer: B.** Python hides the hardware so you reason about names and objects; it is not faster or leaner.

<Fold title="Full explanation">

A Python program does not describe what the hardware does. It describes the behaviour of an **abstract machine**, the model of computation the language defines, in which names refer to objects, objects have types, and memory is allocated and freed automatically. The interpreter maps this model onto the real ("exact") machine. The benefit is that we reason at a higher level, about names and objects rather than registers and addresses. The cost is that we give up direct control of the hardware (A is the opposite of the truth), and Python is neither faster (C) nor more memory-efficient (D) than a language closer to the machine. The <a href={`${import.meta.env.BASE_URL}python-basics/`}>Python basics</a> page develops this model.

</Fold>

### Q2. Kinds of error

A student writes the formula for calculating the area of a circle as `area = 3.14 * radius` instead of `area = 3.14 * radius ** 2`. The program runs without crashing but gives incorrect results. What type of error is this?

- A) Syntax Error
- B) Runtime Error
- C) Semantic/Logical Error
- D) Compilation Error

**Answer: C.** The code is valid and never crashes; it just computes the wrong thing.

<Fold title="Full explanation">

Errors fall into kinds according to when and how they show up. A **syntax error** means the text is not a well-formed program, so Python refuses to run any of it. A **runtime error** means the program is well-formed but something goes wrong while it runs, and an exception such as `TypeError` or `KeyError` is raised. A **logical** (or **semantic**) error is the most dangerous kind: the program runs to completion without complaint but computes the wrong thing. The missing `** 2` is a logical error, since nothing crashes and the result is simply wrong. Only a specification, a test or a careful reader catches such errors. Python has no separate compilation step that could report errors of type D.

</Fold>

### Q3. BNF

In Backus-Naur Form (BNF), what is the primary purpose of production rules using the `::=` symbol?

- A) To define the semantic meaning of Python statements during program execution
- B) To specify how the computer's memory should be allocated for different data types
- C) To formally define the syntax of valid programs using non-terminals and terminals
- D) To determine the runtime behavior of conditional statements and loops

**Answer: C.** A grammar defines syntax (which texts are programs), not meaning or run-time behaviour.

<Fold title="Full explanation">

What counts as a well-formed program is defined by a **grammar**, usually written in **BNF** (Backus–Naur form). A grammar is a set of **production rules** of the form `name ::= alternatives`, read "a *name* is one of these alternatives". Names defined by rules are **non-terminals**, such as `expr` or `stmt`. The literal symbols that actually appear in program text, such as `+`, `while` or a digit, are **terminals**. For example, `expr ::= number | expr "+" expr` says that an expression is a number or two expressions joined by `+`. A grammar says only which texts are programs, that is, it defines **syntax**. It says nothing about what a program *means* when it runs, which is its **semantics**, so A, B and D describe things a grammar does not do.

</Fold>

### Q4. Dynamic vs strong typing

What is the key distinction between Python being "dynamically typed" and "strongly typed"?

- A) Dynamic typing means variables can reference different types, while strong typing means operations are strictly type-checked
- B) Dynamic typing allows implicit type conversions, while strong typing prevents variable reassignment
- C) Dynamic typing refers to runtime speed, while strong typing refers to compile-time checks
- D) Dynamic typing requires type declarations, while strong typing allows flexible operations

**Answer: A.** Dynamic is about *when* types are checked (a name can refer to any type); strong is about *whether* types mix silently (they don't).

<Fold title="Full explanation">

These are two independent properties of a type system, which is why they are often confused.

**Dynamic typing** is about *when* types are checked and *what has* a type. In Python a name has no type of its own; only the object it currently refers to has one. So the same name may refer to an `int` now and a `str` later, and type errors are detected when an operation actually runs. The opposite is static typing, as in C or Java, where each variable has a declared type that is checked before the program runs.

**Strong typing** is about *whether* the language silently converts between types when they are mixed. Python is strongly typed: `"5" + 5` raises `TypeError` rather than guessing. JavaScript is weakly typed and returns `"55"`. Python is therefore both dynamic and strong.

Option B gets both halves wrong: implicit conversion is what strong typing *forbids*, and neither property has anything to do with reassignment. C confuses typing with speed, and D describes static typing.

</Fold>

### Q5. Mixing str and int

What happens when you execute the Python code `"5" + 5`?

- A) It returns the string `"55"` due to implicit type conversion
- B) It returns the integer `10` by converting the string to a number
- C) It raises a `TypeError` because Python doesn't allow mixed-type operations
- D) It returns the boolean value `False` since the types don't match

**Answer: C.** Strong typing: `TypeError: can only concatenate str (not "int") to str`.

<Fold title="Full explanation">

`+` means concatenation for strings and addition for numbers. With a string on one side and an integer on the other, Python does not know which you meant and refuses to guess, so it raises `TypeError` at run time. A is what JavaScript does, which is why JavaScript is called weakly typed. To get either result in Python you must convert explicitly: `"5" + str(5)` gives `"55"` and `int("5") + 5` gives `10`.

</Fold>

### Q6. Type hints at run time

Consider the following Python code with type hints:

```python
def greet(name: str) -> str:
    return f"Hello, {name}"

result = greet(42)   # Passing integer instead of string
```

What happens when this code is executed?

- A) It raises a `TypeError` at runtime because 42 is not a string
- B) It runs successfully and returns `"Hello, 42"` because type hints are ignored during execution
- C) It fails to compile because the type hint violation is detected before runtime
- D) It automatically converts 42 to `"42"` to satisfy the type hint

**Answer: B.** The interpreter does not enforce hints, and the f-string formats any object.

<Fold title="Full explanation">

Type hints such as `name: str` are stored by the interpreter but never checked when the function runs. They are read by separate tools such as mypy, which check them *before* the program runs. Here nothing goes wrong at run time either: the f-string calls `str()` on whatever it is given, so `greet(42)` returns `"Hello, 42"`. D is wrong because no conversion of the argument happens; the formatting inside the f-string is ordinary f-string behaviour that would happen for any object.

</Fold>

### Q7. Walrus vs assignment

Consider the following Python code examples:

```python
# Example 1
result1 = (x := 5)

# Example 2
result2 = (x = 5)
```

What is the key difference between these two examples?

- A) Both examples work identically and produce the same result
- B) Example 1 is valid syntax while Example 2 causes a `SyntaxError` because assignment statements cannot be used in expressions
- C) Example 2 is valid syntax while Example 1 causes a `TypeError` because walrus operator requires function calls
- D) Both examples cause errors because assignments cannot be wrapped in parentheses

**Answer: B.** `:=` is an expression (assigns and yields the value); `=` is a statement and cannot sit inside parentheses.

<Fold title="Full explanation">

An **expression** produces a value, for example `x + 1` or `f(3)`, and can appear anywhere a value is expected. A **statement** performs an action and produces no value, for example `x = 5` or `while …:`. Ordinary assignment `=` is a statement, so `(x = 5)` puts a statement where a value is needed and is rejected as a `SyntaxError` before anything runs. The **walrus operator** `:=`, added in Python 3.8, is an assignment *expression*: `(x := 5)` assigns 5 to `x` and also evaluates to 5, so `result1` becomes 5.

</Fold>

### Q8. Lambdas

Which of the following is a valid use case for lambda expressions?

- B) Creating a simple anonymous function to pass as an argument to `map()` or `filter()`
- C) Writing a function that needs to be called recursively
- D) Defining a class method with detailed documentation strings

**Answer: B.** A lambda is a single expression with no name: ideal for short throwaway functions.

<Fold title="Full explanation">

A **lambda** is an anonymous function whose body is a single expression, such as `lambda x: x * 2`. It cannot contain statements, so loops and multi-line logic (A) are impossible. It has no name to call itself by, which makes recursion (C) awkward, and it has no docstring (D). What it does well is a short function used once, typically passed to `map`, `filter` or `sorted`. ## Correctness: specifications and invariants (Q9–Q12)

### Q9. Ghost variables

Consider this Python swap function with verification:

```python
def swap_verified(x, y):
    original_x, original_y = x, y   # Capture initial values
    temp = x
    x = y
    y = temp
    assert x == original_y and y == original_x, "Swap failed!"
    return x, y
```

What is the purpose of storing `original_x` and `original_y`?

- A) To create backup copies in case the swap operation fails
- B) To preserve the initial values for verifying the swap worked correctly
- C) To optimize memory usage by reusing variable names
- D) To enable the function to work with different data types

**Answer: B.** They are ghost variables: they let the final `assert` refer to the starting values.

<Fold title="Full explanation">

A postcondition often needs to compare the final state with the initial one: a swap must leave `x` holding the *old* value of `y`. But by the time the postcondition is checked, the old values have been overwritten. The solution, explained on the <a href={`${import.meta.env.BASE_URL}specifications/`}>specifications</a> page, is to copy the initial values into extra names at the start and never touch them again. These are **ghost** (or auxiliary) variables. They play no part in computing the result, so they are not a backup (A) and nothing is restored from them. Their only purpose is to let the final `assert` refer to the starting values, exactly as `X` and `Y` do in the Hoare triple `{x = X ∧ y = Y} swap {x = Y ∧ y = X}`.

</Fold>

### Q10. The strongest specification

For a function `second_largest(a, b, c)` that finds the second largest of three distinct numbers, which set of assertions provides the strongest and most accurate verification?

- A) `assert result != max(a, b, c)` and `assert result >= min(a, b, c)`
- B) `assert result in {a, b, c}` and `assert result != max(a, b, c)`
- C) `assert result in {a, b, c}` and `assert result >= min(a, b, c)`
- D) `assert result in {a, b, c}` and `assert result != max(a, b, c)` and `assert result >= min(a, b, c)`

**Answer: D.** Only all three conditions together leave the middle value as the one possible result.

<Fold title="Full explanation">

A specification is **stronger** when it rules out more wrong answers. The test is to ask whether any *incorrect* result could pass all the assertions. The first condition says the result is one of the inputs, the second excludes the largest, and the third says the result is at least the smallest. Since the inputs are distinct, the only input that is neither the largest nor below the smallest is the middle one, so all three together pin the result down uniquely.

Drop any one and a wrong answer passes. Without the first (A), a value that is not an input at all, such as the number halfway between the smallest and largest, passes. Without the second (C), the maximum passes. Without the third (B), the minimum passes. This is the same reasoning as the `max_of_three` example on the specifications page.

</Fold>

### Q11. The while rule

Consider this partial implementation:

```python
def find_max(numbers):
    assert len(numbers) > 0
    max_so_far = numbers[0]
    i = 1
    n = len(numbers)
    # Loop Invariant P: max_so_far = max(numbers[0..i-1])
    while i < n:
        if numbers[i] > max_so_far:
            max_so_far = numbers[i]
        i = i + 1
    return max_so_far
```

According to the While Rule for partial correctness `{P ∧ B} C {P} / {P} while B do C {P ∧ ¬B}`, what must be proven about the loop body `C`?

- A) That `C` always terminates regardless of input size
- B) That `C` executes in constant time for each iteration
- C) That if invariant `P` holds and condition `B` is true before `C`, then `P` still holds after `C`
- D) That `C` correctly updates both `max_so_far` and `i` to their final values

**Answer: C.** That is exactly the rule's premise `{P ∧ B} C {P}`: the body preserves the invariant.

<Fold title="Full explanation">

A **loop invariant** is an assertion that holds before the loop starts and after every iteration. The <a href={`${import.meta.env.BASE_URL}hoare-logic/`}>Hoare logic</a> while rule has one premise: if the invariant `P` and the loop test `B` both hold before the body `C`, then `P` holds again after it. Nothing in the rule says the body terminates (A) or runs in constant time (B); termination is a separate question, not part of partial correctness. The body also does not set variables to their *final* values (D): it advances them by one step.

For `find_max`, the invariant says `max_so_far` is the maximum of the first `i` elements. The body compares one more element and increments `i`, which keeps that true. When the loop stops, `i = n`, so `max_so_far` is the maximum of the whole list. The <a href={`${import.meta.env.BASE_URL}loop-invariants/`}>loop invariants</a> page works through several such proofs.

</Fold>

### Q12. Euclid's step

The Euclidean GCD algorithm implementation uses the step `x, y = y, x % y`. Which mathematical property ensures the loop invariant `gcd(x, y) == gcd(a, b)` is maintained after this operation?

```python
def gcd(a, b):
    assert a > 0 and b > 0
    x, y = a, b
    # Loop Invariant: gcd(x, y) == gcd(a, b)
    while y != 0:
        old_x, old_y = x, y
        x, y = y, x % y
    return x
```

- A) `gcd(x, y) = gcd(y, x)` due to the commutative property
- B) `gcd(x, y) = gcd(y, x mod y)` for any integers `x` and `y` where `y ≠ 0`
- C) `gcd(x, y) ≤ min(x, y)` by definition of greatest common divisor
- D) The modulo operation always returns a non-negative integer

**Answer: B.** The pair `(y, x mod y)` has exactly the same common divisors as `(x, y)`, so the gcd is unchanged.

<Fold title="Full explanation">

Preservation needs a fact about numbers that connects the old pair `(x, y)` to the new pair `(y, x mod y)`. Write `x mod y = x − q·y` for some integer `q`. Any number that divides both `x` and `y` also divides `x − q·y`, so it divides `x mod y`. Conversely, any number that divides both `y` and `x mod y` also divides `(x mod y) + q·y = x`. The two pairs have the same common divisors, hence the same greatest one. A and C are true facts about gcd, and D is true of Python's `%` for positive operands, but none of them explains why one step preserves the invariant. At exit `y = 0`, and `gcd(x, 0) = x`, so the function returns `gcd(a, b)`.

</Fold>

## Lists, functions and dictionaries (Q13–Q18)

### Q13. Shallow copies

Consider this Python code:

```python
original = [1, 2, [3, 4]]
copy_a = original.copy()
copy_b = original[:]
copy_c = list(original)

# Only modify through copy_a
copy_a[2][1] = 99
```

Which of the following statements is TRUE after this code executes?

- A) Only `original` and `copy_a` show the change to the nested list
- B) `original`, `copy_a`, `copy_b`, and `copy_c` all show the change to the nested list
- C) Only `copy_a` shows the change to the nested list, while others remain unchanged
- D) `original` remains unchanged because we only modified through `copy_a`

**Answer: B.** All three copies are shallow, so all four outer lists share the same inner `[3, 4]`.

<Fold title="Full explanation">

A name, a list slot or a dictionary value holds a *reference* to an object, not the object itself. Copying a list with `.copy()`, a full slice `[:]` or `list(...)` makes a **shallow copy**: a new outer list whose slots refer to the *same* element objects as the original. For numbers this is indistinguishable from a full copy, because numbers cannot be changed in place. But the third element here is itself a list. All four outer lists hold a reference to that one inner list, so `copy_a[2][1] = 99` changes the inner list that `original`, `copy_b` and `copy_c` also refer to, and all four show `[1, 2, [3, 99]]`.

Replacing a whole slot, such as `copy_a[0] = 7`, would affect only `copy_a`. To copy nested lists too, use `copy.deepcopy`. The <a href={`${import.meta.env.BASE_URL}lists/`}>lists</a> page draws the memory diagrams.

</Fold>

### Q14. Argument order

Consider this function definition and calls:

```python
def create_rectangle(length, width, color):
    return f"A {color} rectangle {length}x{width}"
```

Which of these function calls is INVALID?

- A) `create_rectangle(10, 5, "blue")`
- B) `create_rectangle(color="green", width=8, length=12)`
- C) `create_rectangle(10, color="orange", width=7)`
- D) `create_rectangle(length=10, 5, "blue")`

**Answer: D.** A positional argument may not follow a keyword argument: `SyntaxError`.

<Fold title="Full explanation">

A call may pass arguments by position, by keyword (`width=8`), or both. Python's rule is that all positional arguments come first, because once a keyword argument has appeared there is no longer a well-defined "next position" to fill. D breaks the grammar of calls and is rejected with `SyntaxError: positional argument follows keyword argument` before anything runs. C mixes the two in the allowed order, and B shows that keyword arguments may come in any order among themselves.

</Fold>

### Q15. Mutating vs rebinding

Consider this Python function:

```python
def process_data(data, value=0):
    data.append(value)
    value = value + 1
    return data, value

original_list = [1, 2, 3]
original_num = 10
result_list, result_num = process_data(original_list, original_num)
```

What are the values of `original_list` and `original_num` after this code executes?

- A) `original_list = [1, 2, 3]`, `original_num = 10`
- B) `original_list = [1, 2, 3, 10]`, `original_num = 10`
- C) `original_list = [1, 2, 3, 10]`, `original_num = 11`
- D) `original_list = [1, 2, 3]`, `original_num = 11`

**Answer: B.** The list is mutated in place, which the caller sees; the integer is only rebound locally.

<Fold title="Full explanation">

When a function is called, each parameter becomes a new local name bound to the object passed in. **Mutating** the object, as `data.append(value)` does, changes the shared object, so the caller sees the change. **Rebinding** the name, as `value = value + 1` does, makes the local name refer to a new object and leaves the caller's object untouched. Integers are immutable, so arithmetic on them always creates a new object and can only ever rebind. So `original_list` becomes `[1, 2, 3, 10]` while `original_num` stays 10. The returned `result_num` is 11, but that is a different object in a different name. The <a href={`${import.meta.env.BASE_URL}functions/`}>functions</a> page explains argument passing in detail.

</Fold>

### Q16. Functions in a list

Consider this Python code:

```python
def double(x):
    return x * 2

def square(x):
    return x ** 2

operations = [double, square]
result = operations[1](5)
```

What is the value of `result` after this code executes?

- A) 10
- B) 25
- C) 7
- D) 32

**Answer: B.** `operations[1]` is `square`, and `square(5)` is 25.

<Fold title="Full explanation">

Functions in Python are **first-class values**: a function is an object like any other, so it can be stored in a list, passed as an argument or returned. `operations[1]` evaluates to the function object `square` (lists are indexed from 0), and the following `(5)` calls it. A is what `operations[0](5)` would give.

</Fold>

### Q17. Dictionary values are shared

Consider this Python code:

```python
student = {
    "name": "Bob",
    "age": [22, 24, 26],
    "major": "Computer Science"
}

std_age = student["age"]
std_age[1] = 0
```

What is the value of `student["age"]` after this code executes?

- A) `[22, 24, 26]`
- B) `[22, 0, 26]`
- C) `[0, 24, 26]`
- D) `Error: cannot modify dictionary values`

**Answer: B.** `student["age"]` returns the stored list itself, not a copy.

<Fold title="Full explanation">

The same fact as Q13: a dictionary value is a reference. `student["age"]` hands back a reference to the list stored in the dictionary, so `std_age` and `student["age"]` name the same list. Setting `std_age[1] = 0` changes that list, and the dictionary sees `[22, 0, 26]`. Had the code *rebound* `std_age` instead, for example `std_age = [0]`, the dictionary would be unaffected. The <a href={`${import.meta.env.BASE_URL}dictionaries/`}>dictionaries</a> page covers this aliasing.

</Fold>

### Q18. KeyError

Which of the following dictionary operations would cause a `KeyError`? (Using the same `student` dictionary as Q17.)

- A) `student.get("phone", "Not provided")`
- B) `student["name"] = "Alice"`
- C) `student["phone"]` when `"phone"` key doesn't exist
- D) `student.update({"age": 21})`

**Answer: C.** Subscripting needs the key to be present; the other three never raise for a missing key.

<Fold title="Full explanation">

The ways to read and write a dictionary differ in how they treat a missing key. Subscripting, `d[k]`, has the precondition that `k` is in `d` and raises `KeyError` otherwise. `d.get(k, default)` never raises and returns the default for a missing key. Assignment `d[k] = v` adds the key if it is missing and replaces its value if it is present, and `d.update(other)` does the same for several keys at once.

</Fold>

## AVL trees (Q19–Q20)

### Q19. What the validator misses

Consider this AVL tree node validation function:

```python
def validate_avl_node(node):
    if node is None:
        return True

    # Check balance factor
    balance = get_balance(node)
    assert -1 <= balance <= 1, f"Node {node['value']} has invalid balance: {balance}"

    # Check BST property
    if node['left'] is not None:
        assert node['left']['value'] < node['value'], "Left child violates BST"
    if node['right'] is not None:
        assert node['right']['value'] > node['value'], "Right child violates BST"

    # Recursive validation
    return (validate_avl_node(node['left']) and
            validate_avl_node(node['right']))
```

Which key AVL tree property is NOT being verified by this function?

- A) Balance factor constraint (−1 ≤ balance ≤ 1)
- B) BST ordering property (left < parent < right)
- C) Height calculation correctness
- D) Structural integrity of left and right subtrees

**Answer: C.** `get_balance` reads the *stored* heights, and nothing recomputes a height from the children.

<Fold title="Full explanation">

A tree is a valid AVL tree when three separate conditions hold at every node: **BST order** (everything in the left subtree is smaller, everything in the right subtree larger), **correct heights** (the stored height is 1 plus the larger child height) and **balance** (the balance factor is −1, 0 or 1). A checker is only as good as the conditions it actually verifies. This function checks the balance factor, but with stored heights. If an insertion forgets to update a height, the balance check is checking the wrong numbers, and the function cannot tell.

The function has a second weakness that was not among the options: it compares each node only with its immediate children, but BST order is a condition on whole subtrees.

<Callout type="warning" title="A common mistake">
Checking only parent and child is **not** enough for a BST. In the tree `5 → (2 → (1, 6), 8)`, every parent-child pair is ordered, but 6 sits in the left subtree of 5. A full check passes down the allowed range (`lo`, `hi`) and recomputes each subtree's real height. See <a href={`${import.meta.env.BASE_URL}recursion-bst-avl/`}>Recursion, BST & AVL</a>.
</Callout>

</Fold>

### Q20. The best post-insert assertion

For an AVL tree insertion function, which assertion would BEST verify that the operation maintains both BST and AVL properties, using the `validate_avl_node` function defined in Q19?

- A) `assert root['value'] is not None`
- B) `assert search_node(root, inserted_value) is not None`
- C) `assert validate_avl_node(root) == True`
- D) `assert get_height(root) == old_height + 1`

**Answer: C.** It is the only option that checks balance and order at every node.

<Fold title="Full explanation">

The candidates differ in strength. A and B confirm something true of any correct insert, but a tree that has lost its balance or its order would pass both. D is not even true of a correct insert: most inserts leave the height unchanged, and a rotation can absorb the extra level, so a correct tree would fail it. Only C checks the balance and order properties at every node, so it is the best of the four, even with the weaknesses noted in Q19. </Fold>
